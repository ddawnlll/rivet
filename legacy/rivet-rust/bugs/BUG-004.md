# BUG-004 — Process-group termination on timeout

**Status:** FULLY VERIFIED (WINDOWS JOB OBJECT + UNIX PROCESS-GROUP) / REVIEW PROTOCOL-LIMITED  
**Priority:** P1

## Symptom and evidence

[OBSERVATION] Runtime and ExecGate previously relied on child-only `kill_on_drop(true)` and had no process-group/session or descendant termination path.

[INFERENCE] A timed-out command could leave a spawned descendant alive.

## Root cause and discriminating observation

[OBSERVATION] On Windows, the implementation creates a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigns the child, and explicitly terminates the job on timeout.
[OBSERVATION] On Unix (including macOS Darwin), the implementation calls `libc::setpgid(0, 0)` in `pre_exec` and kills the negative process-group ID via `libc::kill(-pgid, libc::SIGKILL)` upon timeout.
[OBSERVATION] The Unix process-group test `timeout_terminates_the_process_group` in `crates/rivet-runtime/tests/runtime_boundary_test.rs` was executed on macOS Darwin (`target/debug/deps/runtime_boundary_test-9984ba69862e087c`): 1 passed, 0 failed in 1.02s.

## Final diff summary

[OBSERVATION] Both Runtime (`crates/rivet-runtime/src/lib.rs`) and ExecGate (`crates/praxis/src/gates/exec_gate.rs`) use the managed-child abstraction. Unix creates a process group and kills `-pgid`; Windows assigns a Job Object and terminates the job. Timeout paths terminate and reap all descendants.
