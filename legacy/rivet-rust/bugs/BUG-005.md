# BUG-005 — TUI cancellation was UI-only

**Status:** IMPLEMENTED / FULL-GATE VERIFIED; REVIEW PROTOCOL-LIMITED  
**Priority:** P1

## Symptom and evidence

[OBSERVATION] Esc/Ctrl-C previously changed `is_processing` but did not retain a cancellation handle for the spawned Harness operation.

[INFERENCE] The UI could report cancellation while the operation continued in the background.

## Root cause and discriminating observation

[OBSERVATION] `cancellation_drops_an_in_flight_operation` proves a pending operation is dropped when the cancellation receiver wins. `escape_cancels_processing_and_marks_harness_cancelled` proves the real Esc handler sends the signal, calls `HarnessCore::cancel`, sets `RunPhase::Cancelled`, and clears processing state. Receipts: [.rivet/audit/evidence/BUG-005-v3-targeted.txt](/C:/Users/dresden/Documents/rivet/.rivet/audit/evidence/BUG-005-v3-targeted.txt), [.rivet/audit/evidence/BUG-005-escape-v3.txt](/C:/Users/dresden/Documents/rivet/.rivet/audit/evidence/BUG-005-escape-v3.txt).

## Final diff summary

[OBSERVATION] TUI model/goal tasks now race the operation against a oneshot cancellation receiver. Esc/Ctrl-C sends the receiver signal, calls the Harness cancellation path, and updates UI state. No key binding or UI layout was redesigned.
