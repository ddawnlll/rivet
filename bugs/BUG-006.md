# BUG-006 — Verity pipeline executes commands after earlier gate failure

**Status:** OPEN / BLOCKED-UNSTABLE-TREE  
**Priority:** P1  
**Scope manifest:** `crates/praxis/src/pipeline.rs`, gate tests, no API/dependency changes.

## Symptom and evidence

[OBSERVATION] `VerityPipeline::run` evaluates SchemaGate, LockGate, EvidenceGate, and WiringGate, then unconditionally invokes `ExecGate::execute_all` (`crates/praxis/src/pipeline.rs:68-105`). No prior-verdict guard is visible between these stages.

[INFERENCE] A plan that fails a safety/schema/evidence gate may still execute its declared commands, violating fail-closed verification and potentially running unsafe or irrelevant work.

## Discriminating observation

Build a plan that deterministically fails an earlier gate while containing a command with a sentinel side effect. Run the pipeline and inspect whether the sentinel was created. The test must not use destructive actions.

## Acceptance criteria

- Earlier fail/hold semantics prevent unauthorized command execution as required by the gate contract.
- Existing successful pipeline ordering and receipts remain intact.
- A regression test proves no command runs after a blocking gate failure.
- Full gates pass.

No patch was made while `praxis` is part of the active edit stream.
